# Two-sector player-ship fixture (preparation only)

These files prepare an opt-in diagnostic for two explicitly created Company ships in the two sectors already held by `X4AuthoritySectorReferenceFixture.State`. No automatic installation, game launch, save or seat assignment is supplied. The one-shot `Create` event requires `player.module == 'custom_creative'`, the matching saved epoch and two distinct sector references. This game-start guard does not establish an isolated profile; the caller must provide one. It creates two small Argon fighter hulls with owner `faction.player`, omits pilot creation, and requests `create_ship/safepos` with plot-box avoidance. The cue checks owner, macro, sector, operational state, empty pilot reference, and that neither object is the active player ship, docked or internally stored. The two ship and sector references and the fault/pending state are saved in the cue. If any step fails, creation is not retried: a partial object can remain, so discard the isolated test world.

`authority_player_sector_evidence.verify` checks a saved marker, exact cue fields and saved epoch, unique saved component references, small-ship macro and player owner, and sector ancestry with a zone parent and `connection="space"`. It relies on the caller to supply a confirmed, exclusively fenced checkpoint and expected epoch/marker. The marker parser checks the compressed bytes against checkpoint SHA and size; neither this verification nor an MD reference proves which bytes X4 loaded. The expected new cue serialization is inferred from other native fixtures and is **not yet observed** for this fixture. Unknown formats fail closed.

`authority_player_fixture_marker.xml` is a separate test script named `X4AuthorityPlayerFixtureMarker`; the archived one-shot `X4AuthorityCheckpointMarker.Store` must remain intact. The fixture evidence checker requires the new script's `MarkerState`, not the archived marker. `PlayerFixtureBridge` prepares the normal published-checkpoint identity and native receipt checks with the new marker and saved-fixture verification before confirmation. Its `save()` deliberately always refuses: no validated live fixture-readback gate exists yet. These are offline-tested components only, not an installable or runnable X4 harness. The archived legacy version-1 checkpoint needs its own validated staging path; the standard marked-recovery stager cannot accept its manifest/old marker. A future runner must route the private bridge marker event to the new script, preserve all archived saved cues, and establish live evidence before enabling any save.

The cue emits its local parent, local position, hull and pilot values for later inspection. They are not yet parsed into finite sector-relative coordinates or a verified hull/collision baseline. `safepos` is the engine's position search, not a proof of complete collision clearance, absence of later collisions or safe operation. No assumption is made about zone-to-sector transformations or the completeness of collision detection. The schema accepts the XML but does not execute its expressions or establish the meaning of an empty pilot in a running X4 instance. Before any use as a control-test checkpoint, an isolated native harness must check those facts, preserve the actual parent/frame, verify positions and hull and abort on missing, ambiguous, damaged or visibly unsafe observations. This preparation makes no claim about runtime behavior, autonomous movement, a seat being usable, server authority, networking or gameplay.

Research in the installed game's scripts identified `GetComponentData(ship, 'assignedpilot')` as an assignment observation and the MD properties `ship.controlpostslot.{controlpost.aipilot}` and `slot.component.slotactor.{slot}` as a control-post reservation observation. See [the local research](AUTHORITY-PLAYER-PILOT-RESEARCH.md). A future probe must verify that the slot and component exist and independently calibrate both readings against a known piloted NPC and the unpiloted test ships. An absent assigned pilot and an unreserved slot do not by themselves establish physical seat availability or successful player control. Suppressed MD errors cannot be treated as an empty seat.
